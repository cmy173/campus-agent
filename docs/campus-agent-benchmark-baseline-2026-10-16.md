# Campus Agent Benchmark 基线（2026-10-16）

## 实测范围

- 场景目录：33 项，基础 5、校园业务 8、多工具 6、智能理解 6、异常 8；本轮已跑三个唯一自然语言场景。没有把其余未跑场景填成通过或失败。
- 工具基础层：`tools/audit_agent_eval.py` 的 20 个内存合成领域工具/传输用例 **20/20 通过**。它没有调用模型、校园网络或真实账号。
- 正常 Agent 请求入口：真实本机 API → 独立会话 → 正式 Harness/DeepSeek provider → 事件读取。Provider 配置为本地已启用的 `deepseek-flash`；密钥没有读取或导出。
- 校园服务：用户在受控窗口完成登录后，`campus.status` 仍报告教务连接未授权、缓存为空；`connections.status` 报告学在浙大连接可用并有先前缓存。测试没有把缓存状态当作本次远端同步成功，也没有重复登录。

## 评测器修正记录

第一条 BAS-03 trace 实际包含搜索和网页访问，但旧解析器只识别了领域工具事件，未识别 SDK 的 `harness_event → data.type=tool/call`，错误标成“无工具调用/失败”。修正事件识别后，首次与复测分别识别 9 次和 6 次真实工具调用。

随后真实 BUS-01 trace 显示同一调用被 SDK `tool/call` 与后端 `tool_started` 同时记录，旧指标将 9 次调用报为 18 次。评测器已改为 native SDK 轨迹存在时以其作为调用计数来源，并保留后端工具耗时。对**同一条保存轨迹**重算后，工具数从 18 校正为 9；这是可复现的**评测器正确性改进**，不代表 Agent 性能改善。benchmark 现在会对账户数据工具结果和依赖账户数据的最终回答保存摘要、哈希与状态，隐去课程/教师等明细。

已新增模型调用耗时/工具列表事件（适用于走后端 `/internal/model` 的 provider）和领域工具耗时；当前本机官方 Harness provider 直连模型，SDK 提供了模型轮数、token 用量、工具名称与工具事件时间戳，模型/工具耗时只能根据相邻事件估算。原生请求的完整可见工具 schema 列表与单工具精确耗时仍标记不可用/估算。

## 已证实与待证假设

**已证实**

- 当前本地模型可通过正常 Agent API 完成普通对话；两次公开网页检索均实际执行了 Harness 搜索/抓取工具。
- SDK 轨迹暴露并已记录工具调用参数、返回结果、模型轮次、usage 和相对事件时间；内部 API 模型桥接现在额外记录实际模型 wall time、请求可用工具名与所选工具名。
- WebVPN/教务登录闭环没有实测证据。用户完成受控浏览器登录后，当前 API 的 `browser_session_authorized` 和教务 `connected` 仍为 false；下一步需确认浏览器授权交接与会话是否能被同一 API 进程读取。
- 全量复测前应配置可信 provider 定价，否则 API 美元成本不能计算。
- BUS-01 的调用序列可证实：读状态、连接、课程列表；`campus.query` 与 `campus.sync` 各以 `platform=zdbk` 调用一次并返回 `UNSUPPORTED`；`campus.academics` 没有得到已确认学期；其后又读任务、重复读课程列表、读计划。已证实的结果是教务课表未完成，回答区分了缓存课程与正式课表。原因更具体地说尚不能归结为“工具不存在”：工具契约支持教务同步，但本次调用没有提供明确学期范围；真实登录是否已授权给这个 API 也没有被 `browser_authorized` 状态证实。重复读取与 `UNSUPPORTED` 后再尝试同步是可疑低效行为，单个场景样本不足以调整规划策略。
- BUS-01 的 Agent 结果基于本机现存缓存，且环境不是新建测试账户/空数据库；因此它是带缓存真实端到端观察，不是冷启动校园登录验证。

**待验证，暂不改 Agent 规划或提示词**

- BAS-03 工具调用 6–9 次看起来偏多，但单次差异可能来自模型采样；至少对同一模型、冷/热启动各 3 次并人工检查重复 URL 后，再考虑工具 schema 或搜索计划优化。
- 简单对话回答关于课表、成绩、通知、文件导出、提醒等能力的陈述是否准确，需按仓库工具注册/实测能力逐项校验。
- 校园真实服务认证、课程表/作业/通知读取、人工登录后恢复、超时与 WebVPN 故障尚未端到端覆盖。

## 优先级

1. **P0：确认教务授权与学期查询参数**。在受控浏览器检查登录后能否将授权交给当前 API，再分别用只读工具直测明确学期的教务课程查询和缓存学在浙大读取；保留冷/热状态。禁止用不带学期的 `UNSUPPORTED` 结果推断连接器本身不可用。
2. **P1：填满四层记录**。当前直接工具层为已有合成夹具；Harness 与 Agent 层是真实记录；用户体验层需人工复核确认、追问、等待和任务保持。补充真实校园只读直测/授权测试夹具后再完善自动断言。
3. **P1：小批重复**。对 BAS-03 与 3–5 个真实校园场景各重复 3 次，固定 provider/model/权限和缓存条件，记录非确定性范围，保留至少一组 holdout。
4. **P2：模型成本校准**。配置可信价格表或 provider 账单导入，再报告货币成本；目前总模型调用上限默认 60/批、12/任务，不能等同于美元预算。

## 后续小规模实测：通知工具 Schema（2026-10-16）

基线轨迹显示，BAS-05 先取得 `notices` 的有限公开摘要，然后又调用只针对竺可桢学院的 `college_notices`，得到 `UNSUPPORTED`。代码契约核查确认该来源不能补齐全校通知，因此只修改 `campus.query` / `campus.sync` 的工具描述，明确全校通知使用 `notices`，除非用户明确指定且账户可匹配学院来源，否则不尝试 `college_notices`。没有改 Agent loop 或通知执行器。

| 条件 | 次数 | 部分成功 | 平均端到端 | 平均模型调用 | 平均工具调用 | `college_notices` 调用 |
|---|---:|---:|---:|---:|---:|---:|
| 修改前 BAS-05 基线 | 1 | 0/1 可验证（旧评测曾记部分成功） | 80.92 s | 9 | 13 | 1 次，`UNSUPPORTED` |
| 修改后 BAS-05 候选（按当前来源对齐规则重评） | 3 | 0/3 可确认（3/3 不可验证） | 55.61 s | 5.67 | 7.67 | 0 次 |

候选单次耗时为 45.84 s、41.32 s、79.67 s。旧关键词规则曾将三条都记为部分成功；重建报告并采用来源 URL/标题与日期对齐规则后，三条均缺少足够的可核验证据，故改记为不可验证。原始基线最终回答已脱敏，同样不可验证；耗时与调用指标仍可从轨迹重算。候选相较基线少了不适用的学院来源尝试，但基线仅 1 次，运行之间缓存状态与实时网络结果可能变化，因此这只是**方向性证据**，不能宣称成功率或时延已因果改善。下一实验应对同一通知快照、相同缓存与模型配置做旧/新 Schema 各至少 3 次，并人工核查是否优先使用官方来源和答案覆盖范围。

对运行器的只读审查还发现了评分边界问题。本轮已收紧后续评分：单有非空回复标为“不可验证”；`tool_error` 必须在轨迹中找到匹配工具的实际错误结果；归因先检查模型/工具错误，再判断结果利用。报告比较现在保留每个场景的所有重复样本，列出样本数、均值耗时、模型/工具调用及人工确认数；“不可验证”不再作为失败分数参与平均。重建旧批次报告会用当前评测器重算未脱敏轨迹，历史 `evaluator_sha256` 随之更新；不可恢复的已脱敏最终回答仍不重算。

本轮补上了独立 Harness 合约层：在真实 FastAPI model/tool 路由、领域执行器和事件日志上，用固定 provider mock 驱动“模型工具调用 → 参数解析 → 工具执行 → 工具结果回灌 → 模型续答”一整次往返。首跑暴露 `internal_model` 的 `selected_tools` 追踪只读 provider 原始结构、漏读模型桥接已规范化的 `tool_calls`；修复后往返断言通过。运行器现在每批可单独记录 20 项合成工具层和 Harness 合约层的状态。

候选通知 trace 还确认 `web_fetch` 遇到 `WEB_BLOCKED_URL`（域名解析到非公网地址），随后 Agent 仍尝试多个浏览器栏目 URL，其中两个明确返回“栏目不存在”。运行器之前只把 Harness 事件存在视为一般的结果利用问题；现已从 native `tool/result.message.isError` 提取失败工具名/错误码并归到外部依赖，诊断建议使用已登记来源或授权浏览器，不更改网络安全策略、不做域名变体重试。该发现支持环境/网页源故障归因，不能被算作模型或 campus connector 的失败。

场景目录将每项执行模式改为真实 API（当前唯一逐场景执行器），并增加 `capability_state`、`mock_fixture`、`mock_status`、`initial_state`、`preconditions` 与 `run_status`；没有逐场景 mock fixture 就不能标为 `mock`。BUS-05 的实时空教室/座位、INT-05 的提醒工具及 INT-04 的天气实时源缺失均如实标注。ERR-04 的过期会话注入、ERR-05 的 WebVPN 授权目标和故障切换、ERR-07 的页面结构变化、ERR-08 的人工登录后同任务恢复缺少可复现夹具/执行器支持，因此标为前置条件阻塞，默认批次跳过，显式指定则在启动 API 请求前报错。MULTI-04 已改为全校 `campus.query` 通知来源与公网搜索，不再错误要求仅适用于匹配学院的 college notices。

对比命令现在按场景聚合重复样本，并输出时延均值、样本范围、时延变化百分比、工具/模型调用数和效率方向。对照样本环境不匹配时，这些只作描述性参考，不作因果结论。

## 本轮追加实测与评测器改进

- 新增 `runner.py probe` 实测层。通过真实本机 API 读取 `/api/v1/agent/campus/status`、连接状态，并可选对已登记的 `zdbk_public` 通知源发起一次无凭据只读同步。批次 `live-probe-20261016-notices` 中健康与 API 状态正常，xzzd connector `ok`，但校园 workspace `connected=false`、`browser_session_authorized=false`；这些状态不能混为一谈。一次真实通知读取返回 6 条摘要，最新日期 2026-10-12，`completeness=partial` 且警告 `LIMITED_SCOPE`。
- 在当时有效的 provider 配置下，通过正常 Agent API 对 BAS-01 做 3 次独立会话重复（批次 `20261016-120257-6b1fb73f`）：平均 17.75 秒，平均 1.33 次模型调用、0.67 次工具调用；3/3 均“不可验证”，因为问候场景没有确定性事实判定器。工具调用发生频率只有这 3 个样本的描述性统计，不能当成功率或优化结果。
- BAS-05 最新单次真实 Agent 样本（批次 `20261016-120546-f5d1d609`）：46.31 秒、4 次模型调用、8 次工具调用、11,619 输入 / 3,417 输出 Token，部分成功。轨迹包含通知缓存查询、一次通知同步、3 次 `web_search` 和 2 次 `web_fetch`；通知数据最新日期是 10-12。Agent 将其与当天公开采购公告分开说明。自动评分逐条核对了 7 个引用 URL/标题及 6 个日期与已观察工具结果的一致性，全部匹配；它不证明检索覆盖完整或公告对普通学生最相关，故仍是部分成功，需要人工抽查。独立网页查看器无法访问该采购站点，Python HTTPS 请求因本机证书链错误失败；没有关闭 TLS 校验。重复检索只记录为调用数量，语义冗余尚未证实。
- BAS-05 场景现在使用来源对齐检查，`report` 对输入序列未变化的旧轨迹按当前评分规则重评，同时保留 `evaluation_as_run` 和当前 catalog hash，避免评分标准更新后静默覆盖历史评分。实测触发了“一条助手消息被误归为工具结果失败”的根因审计，已修正为只有观察到实际工具结果事件才归入工具结果利用问题。
- 多轮场景运行器现支持同一会话依次提交 `messages`，每轮写入 turn id 与 trace 索引，在总体超时和模型调用预算下合并轨迹；INT-02 与 INT-03 已改为可复现的两轮输入。定向 runner 测试 3/3 通过。

## 续行：评分器校准与 BAS-04 重复实测

- 并行只读审计发现原 `evaluate()` 从未返回“成功”，所以成功率会恒为零。已补 BAS-04 的目标页面抽取判定：关联用户指定 URL 的工具调用与结果，要求非错误读取，再要求回答达到页面内容词项对齐阈值；通用网站提及和单独 HTTP 200 不足以通过。该判定只证明基础抽取对齐，不评判摘要相关性或完整性。新增单测涵盖“可成功”“泛泛回答/无目标调用不能成功”及真实事件不带 `callId`、按 turn/step 关联三种情况。
- 将现有 BAS-04 旧轨迹按新规则重评：原 n=1 样本可验证成功。随后经真实 Agent API 新跑 n=3（批次 `20261016-125506-8b669ee3`）：2/3 成功、1/3 部分成功，平均 15.46 秒、P50 17.25 秒、P95 17.35 秒，平均 1 次工具调用、2 次模型调用；平均输入/输出 Token 为 1,320/549。对比页面列出旧样本与三条新样本；样本数不等、catalog/runner hash 也不同，12% 的描述性时延下降和一条部分成功都不能归因于 Agent 优化。这是评分器可检出成功与非确定性波动的证据，不是 Agent 能力提升的对照实验。
- BAS-03 公网官方文档检索新跑 n=3（批次 `20261016-130728-c264a7d1`）：3/3 部分成功，平均 34.38 秒、P50 32.57 秒、P95 42.50 秒；平均 6.67 次工具调用、4.67 次模型调用，平均输入/输出 Token 为 13,108/2,729。轨迹都有 `web_search` 和 `web_fetch`；由于评分器没有独立核实文档摘要事实，根因记为 J“评分证据不足/动态事实待人工验证”。多次检索只作为轨迹证据，不推定调用冗余；对照报告已生成，但基线与新样本运行条件不配对。
- 计时字段修改后另做 BAS-04 真实单次校验（批次 `20261016-125942-f5aa3caa`）：成功，端到端 18.21 秒，其中首提交前初始化 32 毫秒、提交至完成 18.18 秒、首条 assistant message 14.24 秒、首 Token 延迟仍为空。该样本只验证计时落盘，不并入前述三次对照样本。
- 修正实时探测语义：现在分别记录 HTTP 传输和功能/授权状态。续行实测 API 传输通过，但校园能力为 `blocked`：`browser_session_authorized=false`；智云课堂 connector 为 `service_unavailable`。用户确认已登录受控窗口，但校园工作区仍无持久授权；项目要求在“助手校园查询授权”卡片点击“复用助手浏览器校园登录”并核验身份，Benchmark 不直接调用该授权接口。
