# Campus Agent 持续实施 Goal 提示词

用途：在 Codex 项目聊天中启动或接续可持续推进的实施目标。本文件是执行合同，不表示其中的功能已经实现；当前目标是否运行，应查看 `/goal` 的状态。

建议首轮完成 M0–M2 的核心试用版；下一轮再整合教务/学院通知和复习生成。每个 Goal 都有可独立验收的终点，避免把长期愿景当成无限任务。

## 直接启动

尚未启动本轮目标时，在项目聊天中发送以下内容。若已有相同的 active Goal，不再启动一次，直接使用下方“接续已有实施”：

```text
/goal 请读取 D:/AI/campus-agent/docs/agent-design/goal-implementation-prompt.md，按其中“首轮执行合同”持续实施 Campus Agent 核心试用版，完成 M0–M2 及全部首轮验收条件。以仓库实际代码、可运行程序和测试证据为准；按合同自主推进，不停留在计划或文档。保留已有未提交改动，持续更新进度记录；只有全部首轮验收满足才标记完成。
```

若在其他路径或新工作树运行，把上面的路径替换为实际文件位置。本文件和设计文档目前可能仍是未提交文件；创建工作树前必须将所需文档安全带入新目录，不能假定 Git 会自动复制。

## 接续已有实施

已有相同的 active Goal 时，直接发送普通消息，不需要再次输入 `/goal`。如果状态是 paused，先发送 `/goal resume`。恢复或切换执行目录时可复制：

```text
继续当前 Campus Agent 核心试用版 Goal，沿用 docs/agent-design/goal-implementation-prompt.md 的首轮执行合同，不扩大范围。先读取 D:/AI/campus-agent/docs/agent-progress.md 指向的实际实施目录及其进度记录，核对真实代码、分支和验收证据。从尚未完成的最小可验证增量接续，不重复已经保全的基线、解包或初始化，不覆盖原工作区。继续修改代码、运行相关检查并记录结果，直至 M0–M2 和全部首轮验收满足。测试通过、文档完成或单个阶段完成，都不能替代整体验收。每次交接记录准确目录、下一步命令与未满足条件。
```

如果是另一条全新的聊天，不能假定旧聊天的 Goal 会自动迁移。把上述接续内容作为背景，并用“直接启动”命令在新聊天建立目标；先核对旧任务状态，避免两个执行者同时修改同一实施目录。

## 通用 Goal 提示词模板

后续每轮用下面的结构写目标；将方括号替换为本轮具体内容，验收条目要能被文件、运行结果或测试证据判定。

```text
/goal 在 [仓库或实施目录] 持续完成 [一个有终点的结果]。
先读取 [执行合同、适用 AGENTS.md 和进度记录]，核对已有代码与未提交改动，从当前进度接续。
完成条件：[列出可验证的功能闭环、相关回归、运行验证及交付文件]。仅写方案、接口占位或演示回答不算完成。
可以自主进行 [本地读取、实现、安装公开依赖、合成测试及启动测试服务]；保留已有成果，遵守 [本轮具体权限和外部操作边界]。
按“证据核对 → 实施一个增量 → 相关验证 → 更新进度 → 下一项”持续推进，不等待我反复说继续。
遇到问题先诊断并尝试有依据的替代路径，继续不依赖阻碍的工作。必需外部条件持续缺失时，按 Goal 运行时规则记录阻碍及最小解锁输入；不得伪造验证或标记完成。
恢复时先检查进度和真实状态；只有全部完成条件得到证据支持才标记 complete。用户暂停或预算停止时保存准确交接，不视为成功。
```

## 首轮执行合同

### 目标与产品原则

把 Campus Agent 实施为本地可运行的核心试用版：学生通过一个对话入口查询已有课程作业、理解资料要求、生成并调整学习安排；需要时在同一任务上下文打开原文和日历。

核心目标是减少学生查找信息、选择模块和组织流程的负担。优先复用 DeepSeek Harness 的运行时，复用已有 Python 连接器和业务引擎，增加领域工具与对话界面。

本轮必须交付运行代码、工具使用文档、自动化和浏览器验证证据。新增设计、接口占位、硬编码示例回答、仅能通过模拟 UI 展示均不算完成。

### 必读材料与事实核对

先读取当前工作区适用的 AGENTS.md，以及 `docs/agent-design/` 下的 README、review-2026-10-13、product-and-architecture、tools、workflows、deepseek-harness 文档。

开始时核实 git status、远端分支、发布包、可用运行环境与已有成果。此前审阅发现 main 的源码 ZIP、仓库展开源码和本地未提交增量不一致；这是需要重新核实的历史事实，不可盲目沿用旧 SHA、临时路径或测试数量。

设计文档是目标和依据，不是实现现状。如果代码或上游 API 与文档不同，先确定证据，进行最小合理调整，并记录决策。不要为了照抄文档重写已经可靠的能力。

### M0：整理可追溯源码基线

1. 保全当前工作区已提交和未提交成果，记录哪些来自原有改动、哪些由本轮产生。
2. 在隔离目录或合适的 codex/ 分支整理学习工作台源码；核验发布包清单，记录来源提交、包哈希、解包位置和与当前代码的关系。
3. 不用 ZIP 覆盖原工作区，不拼接两套数据库，不自动迁移真实学生数据。需要重构时使用独立合成数据库。
4. 选定唯一实施基线，建立可重复的依赖安装、启动和测试入口。
5. 获取官方 DeepSeek Harness，固定可复现版本/提交与依赖锁，记录许可证；实际检查其 API 和配置。

M0 通过条件：交付源码可追溯；原有工作完整保留；另一干净目录能按说明重建环境。M0 完成后直接进入 M1，不以“方案准备好了”结束 Goal。

### M1：接入真实 Harness 运行时和只读工具

1. 采用固定版本的 Harness 运行时，以受控插件/桥接调用现有 Python 服务；禁止用自写循环或伪造的 Harness 类冒充已接入。
2. 第一批工具至少覆盖：连接状态、课程查询、作业查询、资料列表/检索/读取、本地任务查询、当前计划查询、后台任务查询。
3. 每个工具交付严格 schema、实际适配器、使用说明、来源/覆盖/时效字段、错误处理和契约测试。
4. 校园身份、对象范围、凭据和业务权限由可信服务端处理，模型不能通过参数指定其他用户或任意文件/网址。
5. 建立会话与当前课程/材料上下文，支持第二轮追问及断线后恢复；记录工具调用与结果，关键事实附正确来源。
6. 学生界面以对话为主入口，日常操作不要求先进入同步中心或完成所有高级设置。保留可用的旧页面作为过渡。

M1 通过条件：真实 Harness 运行时通过受控模型测试适配完成“作业什么时候截止、需要哪些材料”的工具链；事实来自业务服务和测试资料，不是写死的答案；空数据、无依据、过期缓存、课程歧义与错误能正确呈现。

### M2：完成可撤销的安排闭环

1. 接入可用时间读取、任务生成/反馈、计划读取/预览/应用/撤销，按依赖逐项完成。
2. 支持“本周三晚上没空”等本次安排约束；如现有引擎缺失，补最小确定性适配，不能悄悄覆盖长期偏好。
3. 应用前生成可检查的具体方案与差异；尊重锁定安排、实际容量、已提交作业状态和输入版本。
4. 用户明确接受方案后应用；已给出充分授权的可撤销操作不要重复确认。
5. 长任务显示真实 job 状态；用户打断、重试、重复请求和断线恢复不造成重复写入或虚假成功。

M2 通过条件：“安排这周”→预览→“按这个来”→生效→“撤销刚才安排”形成完整闭环；“把剩余任务改到明天”能承接上下文或准确指出时间不足。

### 全部首轮验收条件

以下全部满足才可以标记 Goal complete：

1. 干净环境安装/构建/启动成功，版本与操作说明可复现。
2. 使用实际 Harness 运行时执行调用链；固定版本、实际启用插件和模型可见工具集合有记录。
3. 三个场景可从同一对话入口完成：查询近期重要作业/安排、解释资料要求、预览/应用/撤销本周计划。
4. 工具的成功、空结果、无依据、非法参数、越权对象、过期版本、重复请求、失败与取消路径有适当自动化覆盖。
5. 计划约束由业务逻辑校验；平台已提交与本地学习完成分开；日期精度和未解析内容不被模型补造。
6. 浏览器验证桌面与窄屏主流程，记录操作结果、截图或可复核的浏览器证据；会话和工作区切换不丢失必要上下文。浏览器工具不可用时记录为未完成验收，不能用源码检查替代。
7. 原基线与新增代码的相关检查通过，未通过项已修复或有明确的既有问题隔离证据；不得删除有效测试或放宽断言制造通过。
8. 工具文档、运行说明、变更摘要、限制和验收报告与实际实现一致。

首轮允许使用合成校园数据与受控模型响应做确定性验证，但必须接入真实 Harness 运行时和真实业务适配器。真实校园账户、真实付费模型回答质量和普通学生试点不属于本轮完成条件，必须在验收报告单列“未验证”，保留测试入口。不得将首轮完成宣称为生产就绪或真实用户验收通过。

### 自主推进方式

- 首轮核对后制定依赖顺序，立即实施最小闭环；各阶段通过后继续下一阶段，不等待我回复“继续”。
- 每轮选择一个可验证的增量：读取证据 → 修改 → 相关验证 → 记录结果 → 选择下一项。修复已有失败优先于增加范围。
- 在实施基线创建或维护 `docs/agent-progress.md`，记录当前目录/分支、版本、已完成及证据、未完成、失败尝试、下一步和阻碍。任务恢复时先读此文件并核验真实代码，避免重复开始。
- 维护验收台账：每项条件标记“未开始 / 进行中 / 已验证 / 受阻”，附命令、结果与证据位置。分别记录真实业务适配、受控模型验证和真实账户验证，不能互相替代。进度及日志不得记录密钥、校园会话或令牌。
- 使用简短进展更新说明成果、问题和下一步；不用每轮重写整份设计。文档不能替代实现进展。
- 不反复运行已经通过且未受影响的全量测试。关键接口、依赖或跨模块变化后运行相关回归，最终完成前运行所需整体检查。
- 不新增计划范围外的一级页面、音视频转写、自动报名、学校平台写入、全量历史抓取、通用 Shell 或插件自动安装入口。
- 不把“有 36 项工具设计”理解为首轮必须全部实现；首轮只实现上述闭环所需工具，其他进入后续清单。

### 授权和变更边界

可以在项目或隔离开发目录内自主读取代码、联网查官方文档、获取公开依赖、编写代码和文档、构建、运行本地合成测试、启动本机测试服务。普通可逆实施选择自行决定并记录，不为每一步请求批准。

保留当前未提交修改，不强制 reset、不清空目录、不改变真实账号数据。不要自动提交学校表单、报名、发邮件、公开部署、推送或合并远端。不能把现有密钥或校园会话当作任意付费测试/数据外发授权；需要新增授权时先完成独立工作，再给出具体范围和原因。

现有约束或更高优先级权限要求优先。没有权限的操作不能通过换工具规避。

### 阻碍与停止

遇到失败先判断是环境、依赖、接口、数据还是实现问题；选择有依据的替代路径。不要重复同一失败命令消耗轮次。

某一路径受阻时继续推进不依赖该条件的实现、契约测试和界面工作。缺真实校园账号或付费模型密钥不会阻断本轮合成验收，但不能因此伪造真实结果。

如果必需条件持续不可用，按 Goal 运行时的阻塞规则记录尝试、错误证据、已完成工作和解锁所需的最小输入；满足阻塞条件后标记 blocked，不伪称 complete，也不无限循环。用户要求暂停时才暂停；预算耗尽则保存准确进度，不把预算耗尽当成功。

最终交付：可运行源码位置与分支、固定依赖版本、启动命令、已实现工具清单、三条场景的证据、测试结果、真实验证缺口和下一阶段建议。所有首轮条件满足后结束，不擅自扩大为全产品无限开发。

## 下一轮 Goal：校园数据整合与复习产物

首轮完成后再使用；不要在尚有未完成首轮目标时盲目替换当前 Goal。

```text
/goal 基于已验收的 Campus Agent 核心试用版，继续完成 docs/agent-design 中 M3–M4：将现有教务与学院通知能力通过明确身份映射接入 Harness 校园工具，接入复习材料预检、生成、读取、修订和导出，并在同一对话与工作区完成对应流程。沿用 goal-implementation-prompt.md 的进度记录、授权边界、证据要求和阻碍处理规则。验收必须覆盖旧版与新系统身份隔离、缓存范围与时效、通知附件未解析和日期歧义、材料版本预检、生成幂等、取消恢复、费用与外发范围校验；复用已有业务引擎，保留首轮回归。允许合成账户与模拟模型做确定性验收，但真实数据和真实模型效果必须单独标明未验证。持续实施直到这些流程可运行且相关自动化、浏览器验收和文档全部完成；不以接口占位或计划完成替代产品闭环。
```

## 操作提示

官方文档将 Goals 定义为跨轮持续目标，建议明确结果、证据和边界；支持 `/goal pause`、`/goal resume`、`/goal clear`。实际能否持续执行还受当前运行状态、权限、阻碍和预算限制，不是保证无人值守无限运行。[OpenAI 官方 Goals 指南](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

首次只需发送“直接启动”的那条命令；已有相同目标时使用“接续已有实施”。提示词本身不设置 token 预算，也不会改变已有 Goal 的状态。控制命令及持续执行边界以上述官方文档和当前运行时为准。
