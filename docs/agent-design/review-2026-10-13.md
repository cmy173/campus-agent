## 2. 核心判断

用户的感受有代码依据：当前产品把“工程模块已经做出来”转化成了“学生必须学习的页面和操作步骤”。AI 主要承担局部生成，学生仍负责组织整个过程。

最重要的调整是明确分工：学生负责目标、偏好和必要决定；Agent 负责选择工具、收集上下文、整理证据、计算方案、检查结果和恢复失败。

### 2.1 最新学习工作台：缺少统一的目标入口

源码包 `apps/web/src/components/AppLayout.tsx:20` 附近定义七个一级入口：今日、课程与资源、学习计划、复习卷、同步中心、设置、使用引导；`apps/web/src/app/router.tsx` 默认进入 `/today`。本轮检查的前端路由和后端路由集合未见统一对话/会话编排入口。

用户想问“这周应该先做什么”，需要自行理解课程同步、任务生成、可用时间、计划预览与应用的关系。把入口挪近只能缓解页面负担，不能补齐这种跨模块编排。

### 2.2 复习功能有价值，但准备工作过多

`apps/web/src/features/reviews/ReviewTab.tsx:858` 起是选择材料，919 起为出卷参数，1115 起为备注，1173 起为发送预览与生成。涉及材料版本、片段范围、来源模式、模型配置和题目要求。

这些能力应保留。默认路径应变为“帮我复习微积分第三章”→系统匹配课程与材料→展示范围和建议→按需生成。高级参数留在展开面板；存在歧义的课程或外发材料范围仍需明确。

### 2.3 今日页仍让学生承担流程衔接

`features/today/TodayPage.tsx` 在同步异常时引导到同步中心，在空状态引导去计划页，并提供“由资料生成任务”；完成反馈后又建议去计划页重排。

建议把这些动作变成就地可恢复的会话流程：例如“有一项作业未完成，要按剩余时间重排吗？”应展示差异方案，而非只给一个去另一页的链接。没有计划时，也应该先回答已知的截止事项，而非把生成计划当作获得价值的前置条件。

### 2.4 旧版聊天框尚未承担校园助手职责

当前工作区 `campus_agent/web.py:681` 的 `/api/chat` 主要有两条路径：特定正则识别待办问句；检索上传资料片段并可选调用模型。请求未包含稳定会话 ID，也未在此路径组合课程、成绩、学院通知和学习计划。

`campus_agent/static/index.html` 的首页还同时呈现宣传区、三张统计卡、推荐入口、模型开关和聊天面板。口号承诺“一个对话框”，实际主流程仍要求学生在多个模块操作。

### 2.5 数据和 AI 分散，会让回答范围不清楚

旧版问答模型与通知整理模型分别配置；新版又有独立 provider 配置。新版 `apps/api/app/routers/search.py` 是当前资源版本内的子串检索，旧版 `services.py` 是关键词检索。它们都不能直接等同于“能够理解并跨系统回答校园问题”。

需要统一模型策略和工具输出，不要求所有任务使用同一个模型。课程时间、截止时间和冲突由结构化数据与规则确定；模型负责意图、解释和内容生成。回答必须明确查到了什么、未覆盖什么。

## 4. 优先级建议

1. **P0：确立单一源码基线和能力台账。** 分清发布包、本地增量、模拟与真实验证。冻结新一级页面。
2. **P0：先做好三个对话闭环。** “今天有什么要紧事”“这项要求到底是什么”“按我的时间安排本周任务”。先做可靠的只读答案，再做可撤销的本地安排。
3. **P1：把现有能力封装成工具。** 使用领域对象和稳定 ID；工具文档和契约测试同步交付。不要把所有 HTTP 接口直接暴露给模型。
4. **P1：统一呈现。** 默认对话 + 简短今日提醒 + 按需工作区。同步、来源绑定和模型细节收进上下文操作或设置。
5. **P2：接回复习卷与其他复杂产物。** 先证明信息负担下降，再扩大长耗时生成、字幕和其他平台覆盖。

应暂缓：新的独立功能门户、默认全量历史同步、无依据的真实学分推断、自动报名/作业提交、未证明需求的全校平台铺开。
